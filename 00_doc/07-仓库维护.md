# 仓库维护

给要动这个仓库的人看的。产品本身见 [01-产品概览.md](01-产品概览.md)。

## 固件是 submodule

`02_sw/vendor/vela_sifli` 是 **git submodule**，指向
`https://gitee.com/jinsc123654/vela_sifli.git`，跟踪 `retire-eval` 分支。

```bash
git clone <本仓库> && cd HelmOne
git submodule update --init --recursive          # 首次
```

### 为什么不是直接拷一份

固件有**两份拷贝就是漂移的源头**。本仓库的前身（`openvela/vendor/HelmOne/`）
已经吃过这个亏 —— 最后只能在那棵树的顶层写一张
"PACKAGING SNAPSHOT ONLY，非特殊声明不要改"。submodule 让固件只有一个真身：

- 固件源码只有一个出处：本仓库的 `02_sw/vendor/vela_sifli` 与 openvela SDK 里的
  `vendor/my_vendor` 是**同一个 gitee 仓库的两处 checkout**，靠 commit 对齐。
- **大体积产物不进任何仓库**。作为对照：开发机上的 `vendor/my_vendor` 有 29 GB，
  而 submodule 检出只有 275 MB —— 差的 27 GB 全是 `boot_loader/bin/`（SD 整盘镜像、
  `fat_root.bin`）和 `mkfs/fat/`（打包好的地图），它们本来就在 `.gitignore` 里，
  只在开发机/烧录机上存在。

### 日常在哪边改

`02_sw/vendor/vela_sifli` **不做日常编辑**（submodule 默认是 detached HEAD）。
日常改动在 openvela SDK 的 `vendor/my_vendor` 里做（build / flash / 调试全在那儿），
改完 push，然后回本仓库把指针跟上：

```bash
cd 02_sw/vendor/vela_sifli
git fetch && git checkout retire-eval && git pull
cd ../../.. && git add 02_sw/vendor/vela_sifli && git commit -m "fw: bump to <sha>"
```

> ⚠️ 直接在 submodule 里编辑提交，改动只会活在这一个 checkout 里、和 SDK 分叉 ——
> 这正是要避免的事。

## `.gitignore` 约定

| 位置 | 管什么 |
|---|---|
| 根 `.gitignore` | `.mimosa/`（安全门禁的工具状态）、`04_tools/vmap` 的本地环境与中间产物、Python 缓存、编辑器 |
| `02_sw/esp32/.gitignore` | ESP-IDF 的 `build/`（约 465 MB）、`sdkconfig.old`、`managed_components/` |
| `01_hw/.gitignore` | Altium 打开工程后生成的 `__Previews/`、`History/`、`Project Outputs/` |
| `03_app/flutter/.gitignore` | Flutter 自带的完整规则（`build/`、`.dart_tool/` 等） |

几个**特意保留、没有忽略**的东西：

- `02_sw/esp32/*/sdkconfig` —— ESP-IDF 的常规做法是忽略它只留 `.defaults`，但这里的
  `sdkconfig` 和 `.defaults` 差 2671 行，是**真实生效的配置**，忽略会丢信息。
- `04_tools/vmap/graph.vgrf` —— 属数据集状态，跟固件一起版本化。
- `03_app/flutter/lib/cache/` —— 名字像缓存，其实是**真源码**（Dart 的缓存存储实现）。

判别纪律：**别按目录名猜**。看 `git status -uall` 里"未忽略又未暂存"的文件数是否为 0，
以及索引里待提交的体积，比看目录名可靠。

## 已知的待收敛项

### 1. vmap 工具链有两份

`04_tools/vmap/` 是从固件树分离出来的，但固件树里的原件**没有删**
（`docs/osm/`、`boards/.../ui/bicycle/tools/` 仍在原处，`make_chuzhou_map.sh` 等还在引用）。
三个收敛方向，待定：

1. **固件树删掉、只留 `04_tools/vmap`** —— 最干净，但要先改固件树里
   `docs/osm/make_*.sh`、`docs/font/subset_font.py` 的对内引用。
2. **固件树的 `docs/osm` 改成指向本目录的软链接** —— 零改动成本，但 SDK 树离开本仓库就断。
3. **两份并存、手动同步** —— 成本最低也最容易漂移，不推荐。

**在收敛之前：改 vmap 工具以 `04_tools/vmap/` 为准。**

### 2. 固件仓库的 docs 已精简，留下若干死链

固件仓库的 `docs/` 已从 140 篇精简到 33 篇（只留参赛 pitch + 启动烧录链，
判据是"精简后仍可构建 boot_loader"）。被删的开发文档仍在 openvela 开发树里，
但仓库内有 **44 个文件**还引用着它们：

- 固件仓库根 `README.md` 有 4 条指向已删文档
- `ai/skills/vela-helm-one/**` 5 个文件
- 约 37 个 `.c/.h/CMakeLists/Kconfig/defconfig` 的注释交叉引用

**都是注释和 markdown 链接，不影响编译**，但要收就一次性收。

### 3. `04_tools/vmap` 内的文内互链

有 10 条指向上级 `map/` 与 `font/` 目录的相对链接（形如 `../map/RUNTIME.md`） ——
它们是按**固件树 `docs/osm/` 的位置**写的，搬到 `04_tools/vmap` 之后就指不到了
（`docs/map`、`docs/font` 已随文档精简从仓库移除）。
更麻烦的是 `../map/README.md` 会误落到同名的 `04_tools/vmap/map/`（那里是二进制瓦片）。
修法：改成指向开发树的措辞，或把演示包改名为 `demo_map/`。

## 提交时的门禁

这个工作区有一道写盘/提交前的安全门禁：

- 它会**拦下**通过 Bash 直接写源码（`cp`/`mv`/`sed -i`/重定向到 `.py`），要求改用编辑器；
- `git commit` / `git push` 前会跑扫描，**可能拦住提交**。历史上拦下来的高危全部落在
  `openvela/prebuilts/**` 的第三方测试文件（Mako 的 SSTI 误报），不是本仓库的代码。

遇到拦截先看**报出的路径**：落在 vendored 第三方目录就别去改那些文件，
把该目录加进扫描排除项后原样重推。**判"提交有没有真的进"只看 `git log`**，
不看命令退出码——它可能静默失败。
